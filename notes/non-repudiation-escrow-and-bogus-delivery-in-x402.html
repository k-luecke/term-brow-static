Why Signed Receipts Do Not Prevent Bogus Delivery in x402: Non-Repudiation Boundaries, AuthCaptureEscrow, and Buyer Policy Firewalls

Stating the exact limit of cryptographic delivery receipts: why an Ed25519 signature over (requestHash, txHash, outputHash) establishes unforgeable attribution without recovering unconditionally settled EIP-3009 funds or detecting fabricated data, and what architecture actually closes both gaps.

Kyle W. Luecke 2026-11-17 9 min read Companion: Technical Note 01 →

1. Stating the Negative Boundary Plainly

In Technical Note 01, I documented why HTTP 200 OK paired with an on-chain Transfer(from, to, value) log leaves response bytes unbound to payment, and how paxiom.receipt.v0 closes that transport gap by signing canonical RFC 8785 digests of the request, payment terms, settlement transaction, and delivered output under an authorized seller Ed25519 key.

What must be stated just as plainly is what a signed delivery receipt does not solve. Suppose an autonomous buyer pays 0.25 USDC via x402’s standard exact scheme (EIP-3009 TransferWithAuthorization) for a structured market feed or tool execution, and the seller returns:

HTTP/1.1 200 OK
Content-Type: application/json
Payment-Receipt: eyJyZWNlaXB0VmVyc2lvbiI6InBheGlvbS5yZWNlaXB0LnYwIiwuLi59

{"results": [], "warning": "upstream_degraded"}

Or worse, suppose the seller returns a syntactically valid JSON payload whose schema passes every structural check, whose JCS SHA-256 digest matches payload.delivery.outputHash, and whose Ed25519 signature verifies against /.well-known/x402-keys.json—except the numbers inside the JSON were fabricated without running the promised computation.

In both cases, verifyReceipt (and live on-chain verification) will report a cryptographically valid receipt. Yet the buyer still received bogus delivery. Treating signed receipts as a silver bullet conflates three distinct security properties that sit at different layers of the stack:

  1. Cryptographic non-repudiation & byte binding: Proving which exact payload bytes Seller Key K committed to in exchange for Payment P.
  2. Conditional settlement finality: Ensuring buyer funds are only irreversibly captured after delivery satisfies an agreed acceptance condition.
  3. Semantic or provenance validity: Deciding whether a well-typed response body is factually or computationally genuine rather than plausible noise.

paxiom.receipt.v0 solves (1). By itself, it cannot solve (2) or (3)—though as shown below, neither (2) nor (3) works cleanly without (1).

2. Failure Boundary I: Unconditional Settlement Ordering (exact vs. AuthCaptureEscrow)

In the baseline x402 exact flow, the buyer signs an EIP-3009 authorization transferring USDC directly to payTo, and the facilitator or resource server settles (or broadcasts) that transfer before returning the HTTP response body. Settlement is pay-before-see and irreversible. If the response times out at the reverse proxy, arrives truncated, or contains an empty error envelope, a valid or missing receipt gives the buyer forensic proof of non-performance—like a signed crime-scene photograph—without any on-chain mechanism to claw back settled USDC.

exact (EIP-3009): Sign(payer) → Transfer(payer → seller) → HTTP 200 [bogus] (funds already final)
auth-capture escrow: Sign(payer) → Authorize(payer → Escrow) → HTTP 200 + Receipt → Verify → Capture | Void

Recovering conditional atomicity over HTTP requires decoupling collateral lock from final payout. Coinbase’s open-source AuthCaptureEscrow contract (base/commerce-payments) implements this two-phase state machine on Base around a canonical PaymentInfo struct:

  • authorize: Moves up to uint120 maxAmount from payer into an operator-scoped TokenStore clone, recording capturableAmount bounded by uint48 authorizationExpiry.
  • capture: Executed by PaymentInfo.operator once delivery is confirmed, transferring funds (net of bounded minFeeBps..maxFeeBps) to receiver.
  • void / reclaim: Either operator explicitly voids the hold upon failed delivery (PaymentVoided), or payer reclaims escrowed funds permissionlessly once block.timestamp >= authorizationExpiry (PaymentReclaimed).

Notice the architectural seam left open by AuthCaptureEscrow: the smart contract enforces who may call capture or void (the designated operator), and enforces hard timeout safety (authorizationExpiry), but the EVM has no native visibility into off-chain HTTP responses. An automated operator needs deterministic, tamper-evident courtroom evidence from the HTTP exchange to decide between capture() and void(). That evidence record is where a signed Payment-Receipt belongs: if the seller omits a valid signature, signs the wrong requestHash, or delivers bytes that fail the structural contract, the arbiter rejects capture and voids the hold.

3. Failure Boundary II: “Signed Nonsense” and the Four Decidability Regimes

Even when AuthCaptureEscrow holds buyer funds in escrow until after HTTP delivery, a dishonest seller can sign a structurally valid JSON document containing fabricated values. A SHA-256 hash and an Ed25519 signature attest to authorship and byte integrity, never to empirical truth. Whether an automated buyer or escrow operator can detect bogus content prior to capture() depends strictly on which of four decidability regimes the workload inhabits:

Regime Representative API Workloads Can Escrow Arbiter Detect Bogus Payload Pre-Capture? Role of Signed paxiom.receipt.v0
I. Deterministic Verification SAT/SMT witnesses, SNARK proofs, light-client Merkle/BLS proofs, code synthesis with local test suites, hash preimages Yes (Exact). Local verifier runs P(request, output) == true in milliseconds before releasing capture(). Binds exact input/output pair to paymentInfoHash so a seller cannot replay a valid proof from a different query.
II. Origin Provenance Paid relays of third-party TLS APIs, regulatory filings, enclave-hosted model inference Yes (Origin-bound). Verifier checks zkTLS transcript commitment or hardware TEE quote (Nitro/SGX PCRs). Wraps provenance quote, request digest, and settlement terms under a single auditable seller receipt.
III. Subjective / Open-Ended Unconstrained LLM synthesis, market commentary, heuristic lead enrichment Structural only. Schema, non-empty bounds, and latency SLAs are enforceable; factual quality is not decidable locally. Essential anti-framing primitive for reputation and stake slashing (see below).
IV. Micro-Metered Streams Token-by-token inference, paginated crawls, per-second telemetry via upto or voucher channels Bounded loss (Δ ≤ $0.001). Buyer halts incremental voucher signing on first bad chunk. Pins cumulative voucher sequence to delivered byte digests for dispute & reconciliation logs.

Why Regime III still requires cryptographic seller signatures: When semantic quality cannot be proven before settlement, markets fall back on seller reputation or bonded stake slashing. Without a seller’s Ed25519 signature over (requestHash, txHash, outputHash), reputation systems are trivially gameable in both directions: a negligent seller can claim the buyer tampered with the response locally, while a malicious competitor can fabricate fake “garbage responses” to grief an honest seller’s did:web score. Non-repudiable receipts make bad-output attribution unforgeable, turning subjective quality disputes from unprovable hearsay into signed historical records.

4. Pre-Sign Buyer Exposure: Why Escrow Still Needs a Client Policy Firewall

Focusing exclusively on post-delivery receipts overlooks how autonomous agents lose funds before a response is ever generated. Most early x402 agent integrations wrap a standard HTTP client with an unconstrained wallet signer (fetchWithPayment(url, wallet)). Left unguarded inside a tool-calling loop, an agent is exposed to four pre-sign failure modes:

  1. Dynamic 402 price escalation: An endpoint advertised at $0.005 during discovery returns a PAYMENT-REQUIRED challenge requesting $25.00 (`25000000` atomic USDC) on retry.
  2. Unpinned payTo / operator substitution: A compromised edge route rotates payTo or PaymentInfo.operator away from the origin’s published /.well-known/x402-keys.json / did:web identity.
  3. Retry-loop budget bleed: When an upstream tool returns transient 5xx errors or empty responses after payment, naive agent loops re-invoke the tool dozens of times per minute, silently draining session USDC.
  4. Facilitator & scheme downgrade: Accepting an exact irreversible challenge on a high-value call where buyer policy requires auth-capture escrow with a trusted operator and minimum authorizationExpiry window.

5. Two-Gate Architecture: Buyer Policy Firewall + Receipt-Gated Capture Arbiter

Closing these failure modes without custodial bloat requires placing a thin, deterministic state machine at the seam between the agent’s HTTP client, its signing wallet, and AuthCaptureEscrow:

Agent Tool Call (req)
  │
  ▼
[Gate 1: Pre-Sign Buyer Policy Firewall]
  ├─ Origin allowlist / denylist & TLS origin sanity (preflightX402)
  ├─ Per-call maxAmountAtomic, per-origin rolling cap, & session budget ceiling
  ├─ Scheme threshold: allow `exact` only if amount ≤ microCap; else require `auth-capture`
  └─ Pin `payTo`, `operator`, & seller `did:web` / `x402-keys.json` signer set
  │
  ▼  (authorized within policy)
Sign Payment / Escrow Hold → Execute HTTP Request → Receive (status, headers, bodyBytes)
  │
  ▼
[Gate 2: Post-Delivery Receipt & Content Arbiter]
  ├─ Check HTTP status == 200 & bounded body size
  ├─ Run verifyReceipt(receipt, { output: bodyBytes, expectedRequest, expectedPayTo })
  ├─ Run caller domain predicate: validateContent(parsedBody, req)  [Regime I/II/III checks]
  └─ Emit deterministic settlement action:
       ├─ All checks pass            → CAPTURE (release escrow + archive signed receipt)
       ├─ Missing/invalid receipt    → VOID    (return escrowed USDC; trip origin circuit breaker)
       └─ Predicate / schema failure → VOID    (log signed bogus payload under seller keyId)

This separation keeps each layer honest about its own invariant. Wallets custody keys; AuthCaptureEscrow enforces on-chain collateral holds and expiry timeouts; paxiom.receipt.v0 provides the non-repudiable binding between HTTP bytes and payment terms; and the buyer firewall enforces deterministic spend ceilings before signing while gating escrow capture on both cryptographic receipt validity and workload-specific output checks afterward.
